# Train data sources for the reliability collector

Researched 2026-10-01. The [plan](../../PLAN.md) needs the planned and reported stop times for recurring RE 89 Augsburg Hbf → München Hbf and ICE 1100 München Hbf → Berlin Hbf, plus explicit cancellations. The named services and sample times have **not** been verified for a real date. This collector needs station events, not a nationwide train-position stream.

## Recommendation

Use [DB Timetables](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables) as the first source to test. The current product offers a **Free** plan limited to **60 calls per minute**, with registration, login, and plan subscription. Its [OpenAPI specification](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) provides station lookup, hourly planned timetables, and full/recent change endpoints. The product states **CC BY 4.0**, but also invokes the [Web-Bahnhofstafel usage terms](https://www.bahnhof.de/nutzungsbedingungen-web-bahnhofstafel). Those terms limit *website* use to viewing and checking information and require prior written consent for other uses; they expressly forbid commercial automated extraction and publication without consent. The [marketplace terms](https://developers.deutschebahn.com/db-api-marketplace/apis/nutzungsbedingungen) say private and commercial developers can register, but §§4/6 defer actual data rights to the applicable licence. The interaction of the CC BY grant and linked website terms for **API-based long-term storage and aggregate publication is unclear**; ask DB to clarify before deployment.

The collection timing in the plan now starts before departure. The [OpenAPI description of `GET /fchg/{evaNo}`](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) explicitly says a change is removed when its trip departs that station. It updates every 30 seconds. `GET /rchg/{evaNo}` contains only changes that became known within the **last two minutes**, also updated every 30 seconds. Polling only after the leg ends could lose München departure changes or cancellations. The collector polls and saves changes before and during station events; completed-arrival behavior still needs a live check. If there is no timely observation, classify the day **unknown** under the [plan's rules](../../PLAN.md).

## DB Timetables contract relevant to the collector

The [current OpenAPI schema](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) is version **1.0.274**. It names the base URL `https://apis.deutschebahn.com/db-api-marketplace/apis/timetables/v1`, with XML responses and two required credential headers, `DB-Client-ID` and `DB-Api-Key`. Its endpoints are:

| Endpoint | Documented purpose and timing |
| --- | --- |
| `GET /station/{pattern}` | Find stations by name prefix, EVA number, DS100/RL100 code, or wildcard. Use it to determine and persist EVA numbers for all configured stops. |
| `GET /plan/{evaNo}/{date}/{hour}` | Planned stops in an hourly slice, where `date` is `YYMMDD` and `hour` is `HH`. The schema says planned data is generated many hours in advance and does not change; slices can overlap. It contains planned attributes and no messages. |
| `GET /fchg/{evaNo}` | All currently known station changes. The schema says future changes are included, obsolete changes are removed when the trip departs the station, and the resource updates every 30 seconds. |
| `GET /rchg/{evaNo}` | Subset of full changes first known within the last two minutes, updated every 30 seconds. The documented pattern is to load full changes first, then poll recent changes at intervals shorter than two minutes. |

For identity, the [`timetableStop.id` schema](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) defines a stop ID composed of a daily trip ID, trip start date, and stop index; the daily trip ID may recur on other dates. The [`tripLabel` schema](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) separately supplies train category (`c`) and train number (`n`). Match configured train category/number, stations, nominal time, and service date to a planned stop, then join changes by documented stop ID. Do not key history by train number alone.

The [`event` schema](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) distinguishes planned time/platform/path (`pt`, `pp`, `ppth`) from changed time/platform/path (`ct`, `cp`, `cpth`). It defines `ct` as a **new estimated or actual** arrival/departure time, without a field that unambiguously says which; `clt` is cancellation creation time. [`eventStatus`](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables/api/160160) defines `c` as cancelled, `p` as planned (also used when a cancellation is revoked), and `a` as added. Check both arrival and departure events at the relevant stations. Never infer cancellation or actual punctuality from a missing change record. The product also disclaims completeness and correctness to the extent permitted by law on its [product page](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables).

Timetables is a **station-oriented stop feed**: its four documented endpoints accept a station EVA number or station pattern. None is a vehicle position endpoint. The [GTFS Realtime specification](https://github.com/google/transit/blob/master/gtfs-realtime/proto/gtfs-realtime.proto) likewise distinguishes `TripUpdate` stop events from `VehiclePosition`; the protocol permits producers to discard past stop updates and says an absent `TripUpdate` means no prediction is available. Neither a departure board nor missing realtime data proves a train's nationwide position or completed on-time journey.

## Feasibility check before writing an adapter

1. Ask DB (the product lists `IRIS-TTS.API@deutschebahn.com`) how its stated [CC BY 4.0 licence](https://developers.deutschebahn.com/db-api-marketplace/apis/product/timetables) and linked [station-board terms](https://www.bahnhof.de/nutzungsbedingungen-web-bahnhofstafel) apply to API polling, retaining raw observations indefinitely, and publishing aggregate statistics. The station-board terms explicitly regulate website use and commercial extraction; the [marketplace terms](https://developers.deutschebahn.com/db-api-marketplace/apis/nutzungsbedingungen) defer data rights to the product licence. Obtain a clear answer on this intended use and attribution before deployment.
2. Register and subscribe to the free plan, then query the three stations and real eligible date. Verify RE 89 and ICE 1100, planned stop IDs, exact times, connection feasibility, and ICE 1100's Berlin Hbf stop. No response was available to validate the sample.
3. Poll `fchg` before departure at Augsburg and München; follow the documented `rchg` pattern more often than every two minutes while the journey runs. Persist each observation, its fetch time, full stop ID and event fields. Check cancellation, delay, platform change, revocation, and unchanged cases. Measure when changes vanish from each station.
4. Compare reported arrivals and departures with the plan's five-minute transfer margin. Label inferred unchanged values **no reported change**, never actual on-time. Determine whether the feed's estimated-or-actual `ct` supports the desired *final arrival delay* wording; if not, present it as reported delay. Treat missing data as **unknown**.

## Access and remaining evidence gaps

The official marketplace product, OpenAPI, marketplace terms, and linked Web-Bahnhofstafel terms are reachable. The documented `apis.deutschebahn.com` API gateway is also reachable: unauthenticated `GET /db-api-marketplace/apis/timetables/v1/station/Augsburg` returned **HTTP 401** with `Invalid client id or secret.` (2026-10-01). `data.deutschebahn.com` (OpenAPI `termsOfService` link) and `www.delfi.de` remained inaccessible; the earlier singular `api.deutschebahn.com` is not the current documented Timetables server. Without clarified licence scope, credentials, and a live authenticated API response, **permitted retention/publication, sample-train coverage, practical latency, and completed-stop behavior are not verified**. The nominal 30-second refresh and two-minute recent-change window above are documented API behavior, not measured service performance.
